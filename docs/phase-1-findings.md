# Phase 1 findings — LiteLLM spine, and the direct-connection question

Date: 2026-07-20. Machine: macOS 25.5.0 arm64.
Versions as executed: Claude Code `2.1.207`, LiteLLM `1.93.0`, Ollama `0.30.10`.

Everything below was **run**, not read. Where something could not be run, it
says so.

---

## 1. Headline: Claude Code can point at LiteLLM directly. CCR is not needed.

**Answer: yes.** `claude` and `claude -p` drive LiteLLM's Anthropic-compatible
`/v1/messages` endpoint with no shim, no translation layer, and no
claude-code-router.

What was executed:

```sh
export ANTHROPIC_BASE_URL=http://127.0.0.1:4000
export ANTHROPIC_AUTH_TOKEN=sk-...          # the LiteLLM master key
export MAX_THINKING_TOKENS=0                # see the caveat below
claude --bare --no-session-persistence --tools "" \
       -p "Reply with exactly the word PONG" --model work
# -> PONG      (exit 0)
```

`work` is a **LiteLLM model group**, not an Anthropic model. Claude Code passes
`--model` through to the gateway unmodified, so the model group *is* the unit of
routing — which is exactly what the architecture wants: the ladder, cooldowns
and failover all live in LiteLLM, and Claude Code just names a lane.

Supporting evidence:

- LiteLLM 1.93.0 exposes `/v1/messages` and `/v1/messages/count_tokens`.
- A raw Anthropic-format `curl` to `/v1/messages` round-tripped to Ollama and
  came back as a valid Anthropic Messages response.
- `"stream": true` produced a correct Anthropic SSE sequence
  (`message_start` → `content_block_start` → `content_block_delta` → …).
  Claude Code streams, so this mattered.
- Claude Code's actual request is `POST /v1/messages?beta=true`.

### Caveat — the one real gotcha

Claude Code sends a `thinking` parameter. Backends that do not implement
extended thinking reject it:

```
API Error: 500 litellm.APIConnectionError: Ollama_chatException -
{"error":"\"llama3.2:latest\" does not support thinking"}
```

`MAX_THINKING_TOKENS=0` fixes it. Note that LiteLLM's `drop_params: true` did
**not** strip the parameter, so this must be handled on the Claude Code side (or
by an explicit per-deployment drop rule) — not assumed away.

### Resolution (Phase 2) — done

`.claude-code-router/` is deleted. HANDOFF §2's condition ("if Claude Code runs
against LiteLLM directly, drop CCR and its configs entirely") was met in Phase 1;
Phase 2 acted on it:

- `.github/workflows/taskcapture-ci.yml`'s review job now calls native
  `claude --bare -p ... --model claude-opus-4-8 --tools ""` instead of
  `ccr code -p`, and no longer installs or configures the router. CCR's own
  "think"-task heuristic (undocumented, internal to the tool) is replaced by an
  explicit `--model`, which is strictly more in keeping with the standing rule
  that milestone-gate criteria are pinned to the frontier model and never
  downshifted — explicit beats inferred.
- `scripts/plan.py`'s `do_plan` now calls native `claude -p --model
  claude-opus-4-8` instead of `ccr code -p --model anthropic,claude-opus-4-8`.
- `scripts/local-serve.sh`'s closing message points at
  `litellm.config.yaml`'s local deployment instead of "CCR's local provider".
- `.claude/tiers.local.json` / `tiers.educloud.json` no longer use CCR's
  `provider,model` comma syntax — see `KNOWN_GOOD_VERSIONS.md` for the rung
  rewrite that replaced it.

The one piece of CCR's config that had no direct replacement — routing
"background"/"quick" vs "think"/"deep" tasks to different models by *task
shape*, independent of the capability ladder — is not reintroduced. That
distinction now belongs to `herdr-meters/classify.py`'s triage layer (which
already reasons about task shape) and to the plan/failup split (planning is
always `judgment`-tier; execution walks the `work` ladder). No functionality is
missing; it just moved to where the project already made the same decision.

**Codex CLI remains an open question — deferred to Phase 3, not resolved here.**
It is not installed on this machine, so nothing about its flags, its
`config.toml` custom-provider path, or whether it can point at LiteLLM the way
Claude Code does has been executed. Every Codex-related value in
`herdr-meters/models.json` stays flagged UNVERIFIED until a machine with Codex
installed can run the equivalent of this session's Claude Code test.

## 2. LiteLLM smoke test — all three acceptance criteria met

### (a) One curl round-trips through Ollama ✅

`POST /v1/chat/completions` and `POST /v1/messages` with `model: work` both
returned `PONG` generated by Ollama.

### (b) Local tier down → failover to the next deployment in `work` ✅

Five consecutive calls with both deployments healthy hit **order=1 every time**,
confirming `order` governs selection rather than the `simple-shuffle` strategy
shuffling across tiers. With the local deployment unreachable, the same request
returned `SOVEREIGN_STANDIN_ANSWERED` — i.e. it fell through to order=2.

### (c) `litellm.sensitive.yaml` exposes no non-local model ✅

Loaded 3 deployments, all `ollama/*`, all `http://localhost:11434`. Requests for
`claude-opus-4-8`, `anthropic/claude-opus-4-8` and `gpt-4o` were each refused
with `400 Invalid model name`. The pin holds structurally, by absence — no
runtime check involved. This is now also asserted by
`tests/test_repo_invariants.py`, so a future edit that adds a non-local
deployment fails CI rather than silently widening the blast radius.

### How the smoke test was actually run — read this before trusting it

Two substitutions were necessary, and both weaken the result in ways worth
stating plainly:

1. **The pinned models are not installed.** Neither `qwen2.5-coder:32b` nor
   `qwen2.5-coder:7b` is present; only `llama3.2:latest`. The smoke config
   mirrors the real `work` group's *shape* but substitutes `llama3.2`. So the
   routing mechanism is verified; the models are not.
2. **There is no sovereign endpoint yet**, so order=2 was a ~40-line stdlib
   HTTP server returning a canned OpenAI-format completion. This proves LiteLLM
   reaches order=2 on failure; it proves nothing about Jetstream2.
3. **Ollama was not actually stopped.** It runs here as a long-lived desktop
   app, so instead of killing the user's process the deployment was pointed at a
   closed port. From the router's side this is the identical failure
   (connection refused), but it is a substitution, not the literal test.

The smoke configs live in the session scratchpad, not the repo — they are test
scaffolding, not artifacts worth maintaining.

## 3. What was wrong in the drafted code

Four real defects, all found by execution. Fixed except where noted.

### 3.1 LiteLLM silently dropped every deployment — **the serious one**

`model_info: {tier: local}` etc. `tier` is a **reserved** LiteLLM key with
literal type `free|paid`. Our semantic values failed validation, and LiteLLM
logged `Error creating deployment ... ignoring and continuing with other
deployments` — then started anyway.

Result: `/health/liveliness` said `"I'm alive!"`, and `/model/info` returned
**0 deployments**. A proxy that reports healthy and routes nothing is the worst
possible failure mode for this project. Fixed by renaming to `commons_tier` in
both configs. Recorded in KNOWN_GOOD_VERSIONS.md, and the Phase 5 canary should
assert a non-empty `/model/info` specifically because of this.

### 3.2 The proxy would not start at all

`health_check_interval` is not a valid `router_settings` parameter in 1.93.0 —
LiteLLM hard-fails with an explicit "move it to `general_settings`". Moved it
and `background_health_checks` accordingly.

Also disabled (commented, not deleted) for now: `success_callback: ["langfuse"]`,
`failure_callback`, and `database_url`. Those are Phase 8 items; with them
enabled and nothing provisioned, the config cannot run today.

### 3.3 `--effort default` is silently ignored — a live hazard for the ladder

`.claude/tiers.claude.json` used `"effort": "default"`. The real flag accepts
only `low|medium|high|xhigh|max`. Critically the CLI **does not error**:

```
Warning: Unknown --effort value 'default' — ignoring it and using the default
effort. Valid values: low, medium, high, xhigh, max.
```

So the fail-up ladder would have appeared to escalate effort while doing
nothing of the kind, and the measurement layer would have attributed the
resulting outcomes to an effort level that was never applied. Fixed: `null` now
means "omit the flag", which `failup.py` already handled correctly.
`herdr-meters/models.json` had the same value; fixed there too.

### 3.4 `--model anthropic,claude-sonnet-5` is rejected

`failup.py` builds `--model` from the tier string, and the tiers files used
CCR's `provider,model` Router syntax. Against Claude Code that is a hard 400.
Fixed in `.claude/tiers.claude.json` (now `claude-sonnet-5` /
`claude-opus-4-8`), and the verified flag rules are recorded as a comment at the
call site in `failup.py`.

**Left alone deliberately:** `.claude/tiers.local.json` and
`.claude/tiers.educloud.json` still carry the comma form. Rewriting them means
deciding what replaces it — bare model names, or LiteLLM model groups — and that
follows from the CCR decision in §1. Flagged, not guessed.
